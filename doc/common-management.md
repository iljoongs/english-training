# 공통 관리 — UI/상호작용 공통 규칙

[메인 지시서](../CLAUDE.md)의 보조 문서. 글자 크기 조절, 마우스 오버 학습 팝업의 표시 조건·동작·데이터 구조 등 이 기능 전반에 공통으로 적용되는 규칙을 정의한다.

---

## 1. 글자 크기 조절

텍스트 창에 표시되는 영어 글자의 크기를 사용자가 조절할 수 있도록 한다.

### 1.1 확대/축소(Zoom)

별도의 크기 조절 UI를 상단 툴바에 두지 않는다. 뷰어(`FlowDocumentPageViewer`)가 기본 제공하는 하단 확대/축소(Zoom) 컨트롤로 텍스트 크기를 조절한다.

* 처음에는 `A-`/`A+` 버튼(§26 이전 버전)이었다가, §28에서 읽기 화면 표시 옵션(글꼴/줄간격/여백/테마/밝기) 툴바를 추가하면서 위쪽에 별도의 `크기` 슬라이더로 한 차례 바뀌었다.
* 이후 뷰어 하단에 이미 동일한 역할을 하는 확대/축소 컨트롤이 기본으로 표시되고 있어 위쪽 `크기` 슬라이더는 중복이라 판단해 제거했다. 지금은 뷰어 하단의 확대/축소 컨트롤 하나만 남아 있다.

### 1.2 글자 크기 제한

뷰어의 확대/축소 컨트롤이 자체적으로 최소/최대 배율을 제한한다(컨트롤 기본값을 그대로 사용하며, 별도의 픽셀 단위 최소/최대/증감 값을 앱에서 관리하지 않는다).

기준이 되는 기본 글자 크기(확대/축소 100% 기준)는 18px이다.

---

## 2. 마우스 오버 학습 기능

영어 텍스트에 포함된 특정 단어 또는 표현 위에 마우스를 올리면 해당 단어/표현에 대한 학습 정보를 팝업으로 표시한다.

예:

```text
I was wondering if you could help me.
       ↑
     마우스 오버
```

마우스가 `wondering if`와 같이 등록된 표현 위에 올라가면 해당 표현에 대한 팝업을 표시한다.

---

## 3. 표현 단위 처리

단순히 하나의 단어만 인식하는 것이 아니라 **여러 단어로 구성된 영어 표현**도 인식할 수 있어야 한다.

예:

```text
look forward to
be supposed to
would like to
I was wondering if
as far as I know
```

따라서 마우스 오버 대상은 다음과 같이 구분할 수 있어야 한다.

### 단일 단어

```text
wonder
help
problem
```

### 복수 단어 표현

```text
wondering if
look forward to
be supposed to
as far as I know
```

등록된 표현이 존재하는 경우 가능한 한 **하나의 표현 단위**로 처리한다.

---

## 4. 팝업 표시 조건

팝업에 어떤 정보를 표시할 것인지는 사용자가 선택할 수 있어야 한다.

선택 가능한 조건은 다음 두 가지다.

```text
□ 해석
□ 영작
```

또는 UI 특성에 따라 버튼/탭/체크박스 등의 형태로 구현할 수 있다.

---

## 5. 해석

사용자가 `해석`을 선택한 경우 마우스 오버한 영어 단어 또는 표현에 대한 한국어 해석을 팝업으로 표시한다.

예:

```text
[해석]

look forward to

~을 기대하다
~을 고대하다
```

문장 전체의 해석이 필요한 경우에는 해당 표현이 포함된 문장을 기준으로 해석 정보를 제공할 수 있다.

---

## 6. 영작

사용자가 `영작`을 선택한 경우 해당 표현을 활용한 영어 작문 관련 정보를 팝업으로 표시한다.

예:

```text
[영작]

"~을 기대하다"를 영어로 표현하면:

look forward to

예문:
I look forward to meeting you.
```

영작 정보는 사용자가 영어 표현을 실제 문장에 활용할 수 있도록 구성한다.

가능하면 다음 정보를 포함한다.

* 한국어 의미
* 대응하는 영어 표현
* 영어 예문
* 필요한 경우 문장 구조 설명

---

## 8. 복수 조건 선택

해석 / 영작은 하나만 선택할 필요가 없다.

여러 항목을 동시에 선택할 수 있어야 한다.

예:

```text
☑ 해석
☐ 영작
```

이 경우 팝업에는 해석 정보만 표시한다.

또 다른 예:

```text
☑ 해석
☑ 영작
```

이 경우 두 가지 정보를 모두 표시한다.

---

## 9. 선택 조건이 없는 경우

사용자가 아무 조건도 선택하지 않은 상태에서는 팝업을 표시하지 않는다.

예:

```text
☐ 해석
☐ 영작
```

이 상태에서 영어 단어에 마우스를 올려도 학습 팝업을 표시하지 않는다.

---

## 10. 팝업 동작

### 10.1 표시

사용자가 학습 대상 단어 또는 표현 위에 마우스를 올리면 팝업을 표시한다.

팝업에는 현재 마우스가 위치한 단어/표현을 기준으로 정보를 표시한다.

예:

```text
┌──────────────────────────┐
│ look forward to           │
├──────────────────────────┤
│ 해석                      │
│ ~을 기대하다              │
│                           │
│ 영작                      │
│ I look forward to seeing  │
│ you.                      │
└──────────────────────────┘
```

### 10.2 위치

팝업은 마우스 위치 또는 해당 단어 주변에 표시한다.

팝업이 화면 밖으로 나가는 경우에는 자동으로 위치를 조정한다.

### 10.3 마우스 이동

마우스가 다른 학습 대상 표현으로 이동하면 기존 팝업 내용을 새로운 표현의 정보로 변경한다.

예:

```text
look forward to
       ↓
be supposed to
```

마우스가 이동하면 팝업도 해당 표현에 맞게 변경한다.

### 10.4 마우스가 텍스트 영역을 벗어난 경우

마우스가 학습 대상 텍스트 영역을 벗어나면 팝업을 닫는다.

단, 사용자가 팝업 내부의 내용을 확인하거나 선택할 수 있도록 필요한 경우 약간의 지연 시간을 둘 수 있다.

예:

```text
마우스 오버
   ↓
약 200~300ms
   ↓
팝업 표시
```

실제 지연 시간은 UX 테스트를 통해 조정한다. (본 프로젝트에서 확정한 값은 §26.3 참고)

## 11. UI 구성

전체 UI는 다음과 같은 구조를 기본으로 한다.

```text
┌──────────────────────────────────────────────┐
│ 영어 학습                                    │
├──────────────────────────────────────────────┤
│                                              │
│  [해석] [영작]                               │
│                                              │
├──────────────────────────────────────────────┤
│                                              │
│  I was wondering if you could help me       │
│  with this problem.                          │
│                                              │
│  I look forward to seeing you again.        │
│                                              │
│                         ┌─────────────────┐  │
│                         │ look forward to │  │
│                         │                 │  │
│                         │ 해석            │  │
│                         │ ~을 기대하다    │  │
│                         └─────────────────┘  │
│                                              │
└──────────────────────────────────────────────┘
```

## 12. 데이터 구조

각 영어 단어 또는 표현은 학습 정보를 가지고 있어야 한다.

개념적으로 다음과 같은 구조를 사용한다.

```text
LearningExpression
├── text
├── interpretation
├── writing
└── expression
```

예:

```json
{
   "text": "look forward to",

   "interpretation": {
       "ko": "~을 기대하다, ~을 고대하다"
   },

   "writing": {
       "description": "한국어 '~을 기대하다'를 영어로 표현",
       "example": "I look forward to seeing you."
   },

   "expression": {
       "meaning": "~을 기대하다",
       "usage": "look forward to + noun / gerund",
       "example": "I look forward to meeting you."
   }
}
```

실제 프로젝트에서는 기존 데이터 구조가 있다면 기존 구조를 우선 사용한다. (본 프로젝트의 실제 구현은 §26.2, [doc/expression-management.md](expression-management.md) 참고 — `interpretation`/`writing`/`expression`이 각각 별도 파일로 저장되고, 화면에 표시되기 직전에 `text` 기준으로 병합된다.)

---

## 13. 텍스트와 학습 데이터 연결

화면에 표시되는 영어 텍스트와 학습 데이터가 연결되어 있어야 한다.

예를 들어 텍스트가 다음과 같은 경우:

```text
I look forward to seeing you.
```

학습 데이터에 다음 표현이 등록되어 있다면:

```text
look forward to
```

텍스트에서 해당 영역을 마우스 오버했을 때 `look forward to`에 대한 학습 정보를 찾아 팝업에 표시한다.

---

## 14. 단어 매칭 우선순위

여러 표현이 중복되는 경우에는 더 긴 표현을 우선적으로 매칭한다.

예:

```text
look
look forward
look forward to
```

문장에 다음과 같이 존재한다면:

```text
I look forward to seeing you.
```

`look`이 아니라 가장 긴 일치 표현인 `look forward to`를 학습 대상으로 처리한다.

즉, 기본적인 우선순위는 다음과 같다.

```text
긴 표현
  ↓
짧은 표현
  ↓
단일 단어
```

---

## 15. 학습 데이터가 없는 경우

마우스가 영어 텍스트의 일반적인 단어 위에 올라갔더라도 해당 단어/표현에 대한 학습 데이터가 없다면 팝업을 표시하지 않는다.

예:

```text
문장:
I went to the office yesterday.

등록된 학습 데이터:
went to
```

`went to`에는 팝업을 표시할 수 있지만, 학습 데이터가 없는 단어에는 팝업을 표시하지 않는다.

---

## 16. 선택 상태 관리

해석 / 영작의 선택 상태는 현재 텍스트 창에 적용되는 상태로 관리한다.

예:

```text
해석 = true
영작 = false
```

이 상태에서는 팝업에 다음만 표시한다.

```text
해석
```

사용자가 `영작`을 추가로 선택하면 즉시 다음 상태가 된다.

```text
해석 = true
영작 = true
```

이후 표시되는 팝업에는 두 가지 정보가 모두 표시된다.

---

## 17. 버튼 상태 표시

선택된 조건과 선택되지 않은 조건을 UI에서 명확하게 구분한다.

예:

```text
[해석]   [영작]
  ON       OFF
```

선택된 버튼은 사용자가 현재 활성화 상태임을 쉽게 알 수 있어야 한다.

---

## 18. 글자 크기와 팝업의 관계

영어 텍스트의 글자 크기를 변경해도 마우스 오버 영역과 팝업 기능이 정상적으로 동작해야 한다.

```text
기본 크기 → 뷰어 확대(Zoom) → 큰 글자 → 마우스 오버 → 정상적으로 표현 인식 → 팝업 표시
```

글자 크기를 변경했다고 해서 단어의 인식 범위나 팝업 기능이 깨지면 안 된다.

---

## 19. 성능 요구사항

영어 텍스트가 길어질 수 있으므로 모든 마우스 이동마다 전체 텍스트를 다시 분석하는 방식은 가능한 한 피한다.

권장 방식:

```text
텍스트 로딩
   ↓
학습 대상 표현 분석
   ↓
표현별 영역 생성
   ↓
마우스 오버 이벤트 연결
```

또는 프로젝트의 UI 프레임워크에 맞는 효율적인 방식으로 구현한다.

특히 긴 영어 문서에서도 마우스 이동 시 지연이 발생하지 않도록 한다.

## 20. 예외 처리

다음 상황에서도 오류가 발생하지 않아야 한다.

### 학습 데이터가 없는 경우

팝업을 표시하지 않는다.

### 해석 데이터가 없는 경우

해석을 선택했더라도 해당 데이터가 없다면 해당 영역을 표시하지 않는다.

### 영작 데이터가 없는 경우

영작을 선택했더라도 해당 데이터가 없다면 해당 영역을 표시하지 않는다.

### 모든 데이터가 없는 경우

팝업을 표시하지 않는다.

## 22. 구현 시 중요 사항

다음 사항을 반드시 준수한다.

1. 영어 텍스트는 일반적인 단순 Label/Text 형태가 아니라 **단어 또는 표현 단위로 마우스 오버를 감지할 수 있는 구조**로 구현한다.
2. 단일 단어뿐만 아니라 여러 단어로 구성된 표현을 지원한다.
3. 여러 표현이 겹칠 경우 가장 긴 표현을 우선한다.
4. 해석 / 영작은 독립적으로 선택할 수 있어야 한다.
5. 선택된 정보만 팝업에 표시한다.
6. 선택된 정보에 실제 데이터가 없는 경우 해당 항목은 표시하지 않는다.
7. 표시할 정보가 하나도 없으면 팝업을 표시하지 않는다.
8. 글자 크기를 변경해도 마우스 오버 기능이 정상적으로 유지되어야 한다.
9. 마우스가 다른 단어/표현으로 이동하면 팝업의 내용도 해당 표현에 맞게 변경되어야 한다.
10. 텍스트 영역을 벗어나면 팝업을 닫는다.
11. 팝업이 화면 영역 밖으로 나가지 않도록 위치를 자동 조정한다.
12. 긴 텍스트에서도 불필요하게 전체 텍스트를 반복 분석하지 않도록 구현한다.

---

## 23. 완료 기준

다음 테스트를 모두 통과하면 기능 구현이 완료된 것으로 판단한다.

* **Test 1 — 영어 텍스트 표시**: 영어 문장이 정상적으로 텍스트 창에 표시된다.
* **Test 2 — 글자 크기 증가**: 뷰어 하단의 확대(Zoom In) 컨트롤을 클릭하면 영어 텍스트가 커진다.
* **Test 3 — 글자 크기 감소**: 뷰어 하단의 축소(Zoom Out) 컨트롤을 클릭하면 영어 텍스트가 작아진다.
* **Test 4 — 해석 팝업**: `해석`을 선택하고 학습 표현 위에 마우스를 올리면 해석 정보가 표시된다.
* **Test 5 — 영작 팝업**: `영작`을 선택하고 학습 표현 위에 마우스를 올리면 영작 정보가 표시된다.
* **Test 6 — 복수 선택**: `해석 + 영작`을 동시에 선택하면 두 가지 정보가 하나의 팝업에 표시된다.
* **Test 7 — 선택 해제**: 특정 조건을 해제하면 이후 팝업에서 해당 정보가 표시되지 않는다.
* **Test 8 — 표현 우선순위**: `look`, `look forward`, `look forward to`가 모두 등록되어 있는 경우 `look forward to`를 하나의 표현으로 인식한다.
* **Test 9 — 데이터 없음**: 학습 데이터가 없는 단어에 마우스를 올렸을 때 불필요한 팝업이 표시되지 않는다.
* **Test 10 — 팝업 위치**: 화면 가장자리의 단어에 마우스를 올려도 팝업이 화면 밖으로 잘리지 않는다.
* **Test 11 — 글자 크기 변경 후**: 글자 크기를 여러 번 변경한 후에도 단어/표현 마우스 오버 기능이 정상적으로 동작한다.

## 24. 최종 사용자 동작 흐름

전체 기능의 사용자 흐름은 다음과 같다.

```text
영어 텍스트 표시
      ↓
사용자가 글자 크기 선택
      ↓
뷰어 하단의 확대/축소(Zoom)로 크기 조절
      ↓
해석 / 영작 선택
      ↓
영어 텍스트에서 학습하고 싶은 단어 또는 표현 위에 마우스 이동
      ↓
해당 단어/표현 확인
      ↓

      ↓
팝업 표시
      ↓
다른 표현으로 마우스 이동
      ↓
새로운 표현의 학습 정보로 팝업 갱신
      ↓
텍스트 영역을 벗어나면 팝업 종료
```

## 25. 구현 원칙

이번 기능의 핵심은 단순한 영어 텍스트 표시가 아니라 **영어 텍스트를 인터랙티브한 학습 콘텐츠로 만드는 것**이다.

따라서 UI 구현 시 다음 세 가지 기능이 서로 독립적으로 동작하면서도 자연스럽게 연결되도록 설계한다.

```text
┌──────────────────────────────┐
│        영어 텍스트            │
│                              │
│  [단어] [표현 단위] [문장]     │
│      ↑                       │
│    Mouse Over                │
└──────────────┬───────────────┘
               ↓
        학습 데이터 검색
               ↓
     ┌─────────┴─────────┐
     │                   │
   해석                 영작
     │                   │
     └─────────┬─────────┘
               ↓
          학습 팝업 표시
```

구현 시 기존 프로젝트의 구조와 스타일을 우선적으로 따르되, 기존 구조를 불필요하게 변경하지 않는다. 새로운 기능은 가능한 한 기존 컴포넌트와 데이터 구조를 재사용하여 추가한다.

## 26. 구현 결정 사항 (확정)

지시서 작성 시점에는 저장소에 기존 프로젝트가 없어 아래 항목들이 모호했다. 다음과 같이 확정했다.

### 26.1 기술 스택

**WPF (.NET) 데스크톱 앱**으로 구현한다.

* 영어 텍스트 표시 및 표현 단위 마우스 오버 감지는 `TextBlock`/`Run` 조합 또는 `InlineUIContainer` 기반 커스텀 컨트롤로 구현한다.
* 학습 팝업은 `Popup` 또는 `Adorner`를 사용해 구현한다.

### 26.2 학습 데이터 출처

**로컬 JSON 파일**을 데이터 소스로 사용한다. 외부 API/DB 연동은 하지 않는다. (실시간 번역 기능을 외부 API 연동으로 추가하려는 계획이 있었으나 보류됐다 — §26.5 참고.)

해석/영작은 각각 별도의 JSON 파일(`interpretations.json`/`writings.json`, `%LOCALAPPDATA%\EnglishTraining\`)로 관리하며, 각 파일은 전용 관리 창(단어 관리/영작 관리)에서 CRUD할 수 있다. 읽기 창은 두 파일을 `text` 기준으로 병합해 §12의 `LearningExpression` 형태로 만든 뒤 매칭에 사용한다. 자세한 내용은 [doc/expression-management.md](expression-management.md) 참고. (한때 세 번째 파일 `expressions.json`/"표현 관리" 창이 있었으나 제거했다 — §26.6.)

### 26.3 팝업 타이밍 (§10.1, §10.4 명확화)

* 마우스 오버 시 **표시(show)에만** 200~300ms 지연을 적용한다.
* 마우스가 학습 대상 영역을 벗어나면 **즉시** 팝업을 닫는다 (닫힘 지연 없음).

### 26.4 단어/표현 매칭 규칙 (§14 명확화)

* 매칭 전 텍스트를 **정규화**한다: 소문자 변환 + 구두점 제거 후 비교한다.
  * 예: `Look forward to,` → `look forward to` 로 정규화되어 매칭 대상이 된다.
* **어형 변화(활용형)는 자동 인식하지 않는다.** `look forward to`와 `looked forward to`는 별개의 문자열이므로, 활용형까지 인식하려면 학습 데이터에 별도 표현으로 각각 등록해야 한다.
* 정규화 후에도 최장 일치 우선 원칙(§14)은 그대로 적용한다.

### 26.5 실시간 번역 — 개발 계획 (보류 중, 미구현)

선택한 텍스트를 즉석에서 번역해 보고 싶다는 요청에 따라 실시간 번역 API 연동을 한 차례 구현했었으나, **API 키 발급(결제 계정 등록 등) 절차를 사용자가 아직 진행하지 않기로 하여 보류**하고 코드는 되돌렸다. 아래는 재개 시 그대로 따를 수 있도록 남겨둔 결정 사항과 설계다.

* **API 선정 경과**: 최초에는 네이버 Papago API(`openapi.naver.com/v1/papago/n2mt`)를 검토했으나, 해당 "AI NAVER API"(개발자센터) 엔드포인트가 2025-03-20 종료되어 더 이상 동작하지 않는 것을 확인했다. 후속으로 이전된 Papago(네이버 클라우드 플랫폼 버전, 별도 가입 필요)와 DeepL(2026-07부터 신규 API 가입자는 월 반복 무료 티어 없이 1회성 100만자 Developer 플랜만 제공)도 검토했으나, 가입 절차와 지속 가능한 무료 한도(월 50만자, 영구 반복) 면에서 **Google Cloud Translation API(v2/Basic)**를 최종 후보로 결정했었다.
* **재개 시 막히는 지점**: Google Cloud Translation API는 무료 티어(월 50만자)라도 Google Cloud 콘솔에서 프로젝트에 결제 계정(카드) 등록 후 Cloud Translation API를 사용 설정해야 키가 발급된다. 이 카드 등록 단계에서 보류를 결정했다 — 재개하려면 먼저 이 등록을 완료해야 한다.
* **재구현 시 설계(구현했다가 되돌린 내용, 그대로 재사용 가능)**:
  * 서비스: `Services/GoogleTranslationClient.cs` — `HttpClient`를 받아 `POST https://translation.googleapis.com/language/translate/v2?key={API키}` 호출, 응답에서 `data.translations[0].translatedText` 파싱. `HttpClient`는 `App`이 하나만 생성해 재사용.
  * 설정 저장: `AppSettings`/`AppSettingsStore`에 `GoogleTranslateApiKey` 문자열 하나 추가, `%LOCALAPPDATA%\EnglishTraining\settings.json`에 저장(저장소에는 커밋 안 됨).
  * 설정 UI: `Views/TranslationSettingsWindow.xaml(.cs)` — API 키 입력용 `PasswordBox` 하나, 읽기 창 `관리` 메뉴의 `번역 설정` 항목에서 연다.
  * 사용 위치: 읽기 창 본문 우클릭 컨텍스트 메뉴에 `번역` 항목(복사/단어 등록 사이) 추가, 선택한 텍스트를 번역해 메시지 상자로 표시.
  * 키 미설정 시: 즉시 호출하지 않고 "번역 설정을 지금 할지" 확인창을 띄운 뒤 동의하면 설정 창을 연다.
  * 오류 처리: API 호출 실패/네트워크 예외는 메시지 상자로만 알리고 앱 상태에는 영향 없음.
  * 테스트: `GoogleTranslationClient.ParseTranslatedText`(정적, public)에 대한 JSON 파싱 단위 테스트, `AppSettingsStore`의 `GoogleTranslateApiKey` 라운드트립 테스트.
* **현재 상태**: 위 코드는 모두 되돌려졌고 현재 앱에는 번역 관련 UI/서비스가 전혀 없다(§26.2 원칙 그대로 유지 중). 사용자가 API 키 발급을 완료하면 이 절을 기준으로 재구현한다.

### 26.6 "표현" 카테고리 제거

해석/영작/표현 3개 카테고리로 시작했으나, **표현 카테고리(및 "표현 관리" 창)를 완전히 제거**했다. 해석/영작 2개만 남는다.

* **범위**: `ExpressionEntry`/`ExpressionInfo` 모델, `표현 관리` 창(`ExpressionManagementWindow`), `표현` 체크박스와 팝업의 표현 섹션, `expressions.json` 저장소, `ExpressionMarkdownParser`, `doc/sample-expression.md`를 모두 제거했다. §29의 `학습 > 가져오기`도 단어 줄 → 표현 매핑이 함께 사라져 문장 → 해석 매핑만 남았다(§29 참고).
* **주의**: `ExpressionSpan`(마우스 오버 컨트롤), `LearningExpression`(매칭된 표현 하나를 나타내는 모델), `IExpressionRepository`/`JsonExpressionRepository`(매칭 엔진이 쓰는 병합 저장소)는 이름에 "Expression"이 들어가지만 **표현 카테고리와 무관한 범용 매칭 엔진**이라 그대로 유지했다 — "표현"이라는 단어가 여기서는 "학습 대상으로 등록된 단어/구문"이라는 일반적인 의미로 쓰인다(§3 참고).
* **기존 데이터**: 제거 시점에 `%LOCALAPPDATA%\EnglishTraining\expressions.json`에 실제 데이터(기본 시드 3개 + 사용자가 §29 가져오기로 등록한 항목들)가 남아있었다. 이 파일은 지우지 않고 그대로 두었다 — 앱이 더는 읽지 않지만, 필요하면 나중에 파일 내용을 직접 참고할 수 있다.

### 26.7 "해석 관리" → "단어 관리" 개명 + `표현` 필드 추가

§26.6에서 표현 카테고리(전용 창)를 없앤 뒤, "해석 관리" 창을 실제로는 단어/숙어를 정리하는 용도로 쓰다 보니 이름이 그 쓰임에 맞게 바뀌었다. **"해석 관리"는 화면·메뉴상 이름이 "단어 관리"로 바뀌었고, 필드가 하나 늘었다.**

* **화면 라벨 변경** (내부 C# 타입명은 유지 — `InterpretationEntry`/`InterpretationManagementWindow`/`ShowInterpretation` 등 그대로):
  * 읽기 창 `관리` 메뉴: "해석 관리" → "단어 관리"
  * 읽기 창 툴바 체크박스: "해석" → "단어" (바인딩 대상 `ShowInterpretation`은 이름 그대로)
  * 관리 창 자체: 창 제목 "해석 관리" → "단어 관리", 상단 메뉴 "해석" → "단어", `표현`(Text) 필드 라벨 → `단어/숙어`
  * 학습 팝업의 해당 섹션 헤더: "해석" → "단어"
* **새 필드 `표현`(`InterpretationEntry.Expression`/`InterpretationInfo.Expression`)**: 단어/숙어를 활용한 유용한 표현을 자유 텍스트로 적어두는 용도. 관리 창 우측에 `단어/숙어`(`Text`) · `해석`(`Ko`) 아래 세 번째 필드로 추가됐고, 학습 팝업에도 `해석` 아래 이탤릭체로 표시된다(비어 있으면 그 줄 자체가 숨겨진다 — `NullToVisibilityConverter`가 빈 문자열도 `null`과 동일하게 취급하도록 확장했다).
* **가져오기 md 형식**: `해석:` 라벨과 나란히 `표현:` 라벨(또는 `#### 표현` 소제목)을 지원한다(`LabeledTextParser`가 이미 다중 라벨을 지원해 파서 쪽 변경은 라벨 목록에 `"표현"`을 추가하는 것만으로 끝났다). 자세한 형식은 [doc/expression-management.md](expression-management.md) §5 참고.
* **§26.6과의 이름 중복에 대한 참고**: 이 필드명 `Expression`은 §26.6에서 제거한 "표현 카테고리"(`ExpressionEntry`)와 이름만 같을 뿐 별개다 — 지금의 `표현`은 단어 관리 안의 필드 하나일 뿐, 별도 파일·창·체크박스가 있는 카테고리가 아니다.

### 26.8 `품사` 필드 추가 + 학습 팝업 레이아웃 변경

단어 관리에 네 번째 필드 `품사`(`InterpretationEntry.PartOfSpeech`/`InterpretationInfo.PartOfSpeech`)가 추가됐다. 관리 창 우측에 `단어/숙어` 바로 아래, `해석` 위에 편집란이 생겼다.

* **가져오기 md 형식**: `해석:`/`표현:`과 나란히 `품사:` 라벨(또는 `#### 품사` 소제목)을 지원한다.
* **학습 팝업 레이아웃 변경**: 표현 단위에 마우스를 올렸을 때 뜨는 팝업에서, 단어 섹션의 표시 방식이 바뀌었다.
  * 이전: `단어`(굵은 파란 소제목) → 해석 → (있으면) 표현, 세 줄.
  * 이후: 소제목 없이 **`품사, 해석`**(예: `n, 천문학자들`, 품사가 없으면 해석만) 한 줄 → **구분선** → **표현**. 구분선과 표현 줄은 `표현` 값이 있을 때만 보인다.
  * 이 조합은 `PopupContentData.InterpretationHeader`(계산 속성, `품사`가 비어 있으면 `해석`만 반환)가 만든다.
* **"학습 > 가져오기"와의 연결**: today.md의 단어 줄 형식(§29.1)이 `단어(품사) (해석) (표현)`로 정해지면서, 이 세 괄호가 각각 `PartOfSpeech`/`Ko`/`Expression`으로 그대로 대응된다 — §26.6/§26.7 당시엔 "단어 줄을 보낼 대상이 없다"고 봤지만, `품사` 필드가 생기고 today.md 쪽 형식도 함께 정리되면서 지금은 자동 매핑이 가능해졌다(§29.1 갱신 내용 참고).

### 26.9 단어 관리 가져오기 버그 수정 + 목록 정렬 추가

* **버그 수정 — 단어 관리 창의 "가져오기"가 today.md 스타일 파일에서 빈 항목만 만들던 문제**: 단어 관리 창 자체의 `가져오기`(버튼/메뉴/드래그앤드롭)는 `InterpretationMarkdownParser.ParseMultiple`을 쓰는데, 이건 `### 단어` 섹션이나 `해석:`/`표현:` 라벨을 기대한다. `data/today.md`처럼 압축 단어 줄(`단어(품사) (해석) (표현)`)만 있는 파일을 넣으면 `### `도 라벨도 없어 "단일 항목 폴백"이 걸려 **제목 줄 하나만 있는 텍스트/해석/표현이 전부 빈 항목 1개**로 뭉개졌다(실제 단어들은 전부 버려짐). `TodayEnglishParser`(§29.1)는 이런 파일을 정확히 파싱하므로, 파서가 잘못된 게 아니라 **단어 관리 창의 가져오기가 엉뚱한 파서를 쓰고 있던 것**이 문제였다.
  * **해결**: `InterpretationMarkdownParser.ParseAny(filePath)`를 새로 만들어 단어 관리 창의 `_importParser`로 교체했다. 먼저 `TodayEnglishParser.Parse`로 시도해 한 줄이라도 걸리면 그 결과를 쓰고, 하나도 안 걸리면 기존 `ParseMultipleContent`(`### `/라벨 형식)로 폴백한다. 두 형식이 서로 겹칠 걱정은 거의 없다 — `### `로 시작하는 줄이나 라벨 줄은 애초에 `TodayEnglishParser`의 단어 줄/문장 줄 패턴과 매칭되지 않는다.
* **목록 정렬**: 단어 관리·영작 관리 두 창 모두(`EntryManagementViewModel<T>`가 공유되므로) 좌측 목록이 **`Text` 기준 오름차순(대소문자 무시)으로 기본 정렬**된다 — 창을 처음 열 때, `파일 > 열기`로 다른 파일을 불러올 때 모두 적용된다. 목록 아래 `오름차순`/`내림차순` 버튼으로 언제든 다시 정렬할 수 있다. 정렬은 화면에 보이는 순서만 바꾸고, `_repository`나 저장 파일의 항목 순서는 건드리지 않는다(재정렬 시 현재 선택 항목은 그대로 유지된다).

### 26.10 UI 표시 텍스트를 영어로 전환

앱의 **화면에 보이는 텍스트**(창 제목, 메뉴, 버튼, 체크박스, 필드 라벨, 확인창/메시지박스, 파일 선택 대화상자 필터)를 전부 영어로 바꿨다. **이 문서를 포함한 doc/*.md 스펙 문서 자체는 계속 한국어로 쓴다** — 문서 안에서 UI 요소를 가리킬 때는 지금부터 실제 영어 라벨을 함께 표기한다(예: "가져오기(`Import`)"). 아래는 주요 대응표다.

| 위치 | 한글(이전) | 영어(현재) |
|---|---|---|
| 읽기 창 메뉴 (최초 영어화 당시 — §26.11에서 재구성됨) | 관리 / 학습 | Manage / Study |
| 읽기 창 관리 메뉴 (당시) | 문장 관리 / 단어 관리 / 영작 관리 | Sentences / Words / Writing |
| 읽기 창 학습 메뉴 | 오늘의 영어 / 가져오기 | Today's English / Import |
| 읽기 창 툴바 | 단어 / 영작 / 글꼴 / 줄간격 / 여백 / 테마 / 밝기 | Word / Writing / Font / Line Spacing / Margin / Theme / Brightness |
| 우클릭 메뉴 | 복사 / 단어 등록 / 문장 등록 | Copy / Add Word / Add Sentence |
| 창 제목 | 영어 학습 / 문장 관리 / 단어 관리 / 영작 관리 / 오늘의 영어 | English Training / Sentence Management / Word Management / Writing Management / Today's English |
| 공통 메뉴·버튼 | 파일 / 열기 / 저장 / 다른 이름으로 저장 / 신규 / 가져오기 / 내보내기 / 삭제 | File / Open / Save / Save As / New / Import / Export / Delete |
| 단어 관리 필드 | 단어/숙어 / 품사 / 해석 / 표현 | Word/Idiom / Part of Speech / Meaning / Usage |
| 영작 관리 필드 | 표현 / 설명 / 예문 | Expression / Description / Example |
| 정렬 버튼 | 오름차순 / 내림차순 | Ascending / Descending |
| 학습 팝업 | 영작 | Writing |

* **바꾸지 않은 것**: `.md` 가져오기/내보내기가 인식하는 **라벨 텍스트**(`해석:`/`표현:`/`설명:`/`예문:`/`품사:`, `#### 라벨` 소제목 등)는 그대로 한글이다 — 이건 UI 크롬이 아니라 사용자가 직접 손으로 쓰는 **파일 형식**이라, 여기까지 바꾸면 `data/2026-08-22-word.md` 등 기존에 작성해둔 실제 파일들이 더는 인식되지 않는다. `DefaultLearningData.cs`의 학습 콘텐츠(예: `Ko = "보다"`)도 앱의 핵심 데이터(한국어 뜻 자체)라 당연히 그대로 뒀다.
* 학습 팝업의 `단어` 섹션은 원래도 소제목이 없고 `PopupContentData.InterpretationHeader`(품사, 해석)로만 표시되므로(§26.8) 이번 변경으로 새로 영어화할 라벨이 없었다.

### 26.11 읽기 창 최상위 메뉴 재구성 (`Files`/`Sentences`/`Words`/`Writing`/`Study`)

§26.10에서 영어화했던 `Manage`(Sentences/Words/Writing) + `Study`(Today's English/Import) 2단 메뉴 구조를 없애고, 최상위 메뉴 하나(`Menu`) 아래 **`Files` / `Sentences` / `Words` / `Writing` / `Study` 5개의 하위 메뉴**를 두는 3단 구조로 바꿨다. 관리 창을 여는 동작(`Setting`)은 그대로 남기고, 관리 창을 열지 않고도 읽기 창에서 바로 md 파일을 넣고 뺄 수 있는 `Import`/`Export`를 각 카테고리 메뉴에 추가했다.

```text
Menu
├─ Files      Load / Save / Save As
├─ Sentences  Setting / Import / Export
├─ Words      Setting / Import / Export
├─ Writing    Setting / Import / Export
└─ Study      Today's English / Import
```

* **`Setting`**: 이전 `Manage > Sentences|Words|Writing`과 동일한 동작 — 해당 관리 창을 연다(§26.7 문장 관리, 단어 관리, 영작 관리 각각 [sentence-management.md](sentence-management.md)/[expression-management.md](expression-management.md) 참고).
* **`Sentences`/`Words`/`Writing`의 `Import`**: 관리 창을 열지 않고 `.md` 파일 하나를 선택해 바로 해당 저장소에 병합한다 — 문장은 `TopicMarkdownParser.ParseMultiple`, 단어는 `InterpretationMarkdownParser.ParseAny`(§26.9), 영작은 `WritingMarkdownParser.ParseMultiple`을 그대로 재사용한다. 가져온 뒤 즉시 저장(`Save()`)하고, 단어/영작은 읽기 창의 학습 팝업 데이터도 다시 병합한다(§12).
* **`Sentences`/`Words`/`Writing`의 `Export`**: **선택된 항목 하나가 아니라 해당 저장소의 전체 항목**을 `.md` 파일 하나로 내보낸다 — 관리 창의 `내보내기`(선택 항목 1개, `Format`/`Export`)와는 범위가 다르다. 이를 위해 세 파서(`TopicMarkdownParser`/`InterpretationMarkdownParser`/`WritingMarkdownParser`) 각각에 `FormatMultiple`/`ExportMultiple`을 새로 추가했다 — 항목마다 `### 제목` 구간으로 묶어 기존 다중 항목 가져오기 형식과 그대로 호환된다(라운드트립 가능).
* **`Files`**: 문장 데이터(`topics.json`) 전용이다 — `Load`(다른 `.json` 파일로 전체 주제 목록 교체), `Save`(현재 파일에 저장), `Save As`(새 경로에 저장 후 이후 저장 대상 전환). 단어/영작 데이터의 `.json` 파일 열기/저장은 여전히 각 관리 창의 `파일` 메뉴에서만 가능하다 — 읽기 창에는 문장(주제) 파일 전환만 노출한다(주제 전환이 읽기 화면에 가장 직접적으로 영향을 주는 조작이라는 판단).
* **`Study`**: 기존 `Today's English`(§27.1)/`Import`(§29)에서 변화 없음 — 최상위 메뉴 이름만 유지된다.

## 27. 단어/문장 등록과 "오늘의 영어" (data/today.md)

읽기 창 본문에서 텍스트를 드래그로 선택한 뒤 그 선택 영역 위에서 마우스 오른쪽 버튼을 클릭하면 팝업 메뉴(복사 / 단어 등록 / 문장 등록)가 뜬다. 선택된 텍스트가 없는 상태에서 우클릭하면 메뉴 자체가 뜨지 않는다.

`단어 등록` 또는 `문장 등록`을 클릭하면 선택된 텍스트가 `data/today.md`에 추가된다. 둘 다 같은 파일에 쓰되, 단어는 일반 텍스트 줄로, 문장은 `**굵게**`로 감싸서 한 파일 안에서도 단어와 문장을 한눈에 구분할 수 있게 한다.

* 파일 위치: 저장소의 `data/today.md` (날짜별 파일이 아니라 고정된 파일명 하나다). `%LOCALAPPDATA%`가 아니라 저장소 안 `data/`에 쓴다 — 나중에 사람이 훑어보며 필요한 것만 골라 [해석/영작 관리](expression-management.md)에 직접 옮겨 담기 위한 메모 용도다.
* 파일이 없으면 `# 오늘의 영어` 제목과 함께 새로 만들고, 있으면 이어서 추가한다.
* 형식은 `### ` 같은 헤딩이 아니라 일반 텍스트 한 줄이다. `단어 등록`은 선택한 텍스트를 그대로 한 줄 추가하고, `문장 등록`은 `**선택한 텍스트**`로 감싸 굵게 추가한다.
* 이 형식은 [문장 관리](sentence-management.md)/[해석·영작 관리](expression-management.md)의 "여러 항목" md 가져오기(`### ` 기준 분리)와는 다르다 — 이 파일은 재가져오기용 초안이 아니라 사람이 읽고 골라내는 메모이기 때문에 의도적으로 단순한 텍스트로 남긴다.

```markdown
# 오늘의 영어

deadline

wondering if

**I look forward to seeing you again.**
```

같은 표현을 여러 번 등록하면 중복 확인 없이 그대로 여러 번 추가된다.

### 27.1 "오늘의 영어" 창 (읽기 창 메뉴: 학습 > 오늘의 영어)

`data/today.md`를 직접 열어 읽고 고쳐 쓸 수 있는 별도 창이다. 우클릭으로 등록한 단어/문장을 다듬거나, 뜻/예문을 손으로 채워 넣거나, 필요 없는 줄을 지우는 등 자유 형식 편집이 목적이다.

* 창을 열면 파일 전체 내용을 하나의 텍스트 편집 영역에 불러온다(파일이 없으면 `# 오늘의 영어` 기본 내용으로 시작).
* 상단 `파일 > 저장`으로 편집한 내용을 그대로 `data/today.md`에 덮어쓴다. 특별한 서식 검증은 하지 않는다 — 완전한 자유 텍스트 편집기다.
* 하단에 파일 경로와 크기를 표시한다(다른 관리 창들의 "파일 (크기)" 상태 표시와 동일한 관례).
* 다른 관리 창처럼 여러 개를 동시에 열 수 있다. 단, 같은 파일을 여러 창에서 동시에 저장하면 나중에 저장한 내용이 이긴다(마지막 저장이 우선) — 단일 사용자의 개인용 메모 파일이라는 전제하에 별도 잠금/충돌 처리는 하지 않는다.

## 28. 읽기 화면 표시 옵션 (뷰어 · 테마 · 타이포그래피)

읽기 창의 본문 뷰어는 상위 폴더의 개인 프로젝트 [text-readers](../../text-readers)를 참고해 구현했다. 스크롤형 `RichTextBox` 대신 `FlowDocumentPageViewer`(페이지 형태, 뷰어 크기에 맞춰 자동 페이지 분할)를 사용하며, 종이 질감/다크/세피아 테마와 글꼴·줄간격·여백·화면 밝기 조절을 제공한다.

* **뷰어**: `FlowDocumentPageViewer`. 스크롤 없이 페이지 단위로 표시되며, 방향키(←/→)·PageUp/PageDown과 뷰어 하단의 기본 내비게이션 바로 페이지 이동이 가능하다(별도 구현 없이 컨트롤 기본 제공). 글자 크기 조절도 이 뷰어가 기본 제공하는 확대/축소(Zoom) 컨트롤로 하며, 상단 툴바에는 별도의 크기 조절 UI를 두지 않는다(§1 참고).
* **글꼴**: 상단 툴바의 `글꼴` 드롭다운에서 선택. 한글 타이포그래피용 임베디드 폰트 5종(Noto Serif KR, NanumMyeongjo, RIDIBatang, NanumBarunGothic, Spoqa Han Sans Neo)을 `Assets/Fonts/`에 포함해 배포하며, 시스템에 폰트가 설치되어 있지 않아도 동일하게 보인다.
* **줄간격 / 여백**: 줄간격은 1.0~2.0배 슬라이더, 여백은 좁게/보통/넓게 3단계 프리셋.
* **테마**: 종이(기본, 질감 텍스처 배경) / 다크 / 세피아 3종. 배경·글자색이 함께 바뀐다.
* **화면 밝기(어둡게)**: 0~0.7 슬라이더로 화면 전체에 검은 반투명 오버레이를 씌워 밝기를 낮춘다(야간 독서용).
* **저장**: 글꼴/줄간격/여백/테마/밝기는 변경 즉시 `%LOCALAPPDATA%\EnglishTraining\settings.json`에 저장되어 다음 실행 시 복원된다(§26의 창 크기/위치, 마지막 주제 저장과 동일한 방식). 글자 크기(기본 18px)는 뷰어의 Zoom이 담당하므로 이 목록에서 빠지며, 앱 재시작 시 항상 100% 배율로 초기화된다.
* **기존 기능과의 관계**: 표현 단위 마우스 오버 팝업(§2)과 텍스트 선택 → 우클릭 메뉴(복사/단어 등록, §27)는 뷰어가 바뀌어도 그대로 동작한다 — `FlowDocumentPageViewer`도 `Selection`/`ContextMenu`를 지원하며, `InlineUIContainer`로 삽입한 표현 컨트롤의 마우스 이벤트는 뷰어 종류와 무관하다.
* **가져오지 않은 것**: text-readers에는 페이지 전환 시 슬라이드/페이드 애니메이션과 좌우 클릭 영역(커스텀 페이지 넘김 UX)이 있으나, 읽기 창의 주제 텍스트는 대개 페이지 하나 안에 들어가는 짧은 분량이라 이번에는 이식하지 않았다. 필요해지면 추가한다.

## 29. "학습 > 가져오기" (data/today.md → 단어 관리)

읽기 창 메뉴의 `학습 > 가져오기`는 `data/today.md`(§27)를 읽어 단어 관리(§26.7) 데이터를 자동으로 등록하는 기능이다.

샘플 파일: [doc/sample-today.md](sample-today.md).

### 29.1 today.md에서 인식하는 줄 형식

* **단어 줄** → **단어 관리**(`InterpretationEntry`)로 등록: `단어(품사) (해석) (표현)` — 괄호 세 쌍
  * 예: `Astronomers(n) (천문학자들) (astronomers say/discovered ~)`
  * 첫 번째 괄호 → `품사(PartOfSpeech)`, 두 번째 괄호 → `해석(Ko)`, 세 번째 괄호 → `표현(Expression)`. 세 괄호가 모두 있어야 인식된다 — 괄호가 두 쌍 이하(예전 `단어(뜻) (사용법)` 형식)이면 매칭되지 않고 건너뛴다.
  * 단어와 첫 괄호 사이에 공백이 있어도(`deadline (n) (...)`) 없어도(`deadline(n) (...)`) 똑같이 인식한다.
* **문장 줄** → **단어 관리**(`InterpretationEntry`)로 등록: `**영어 문장**` 바로 다음 (빈 줄을 건너뛴) 첫 줄이 `(한글 번역)`인 경우
  * 예: `**I was wondering if you could help me with this.**` + `(이것 좀 도와주실 수 있는지 궁금했어요.)`
  * `단어/숙어(Text)`에 영어 문장, `해석(Ko)`에 번역을 채운다. `품사`/`표현`은 today.md에 대응하는 내용이 없어 비워둔다.
* **아직 안 채워진 줄**(괄호가 덜 채워진 단어 줄, 번역 줄이 없는 굵은 문장 등)은 조용히 건너뛴다 — 막 등록해서 아직 다듬지 않은 줄이 정상적으로 있을 수 있기 때문이다.
* **영작 관리**(`WritingEntry`)로 가는 매핑은 없다 — today.md에 이에 대응하는 패턴이 없어 범위에서 제외했다.

### 29.2 동작 방식

* `TodayEnglishParser.Parse`가 위 형식을 정규식으로 인식해 `List<InterpretationEntry>`를 만든다(파일 I/O 없이 문자열만 받는 순수 함수라 테스트하기 쉽다).
* `TodayEnglishImportService.ImportContent`가 그 결과를 단어 저장소(`interpretations.json`)에 추가한다. **중복 처리**: 저장소에 이미 같은 정규화 텍스트(§14와 동일한 `TextNormalizer` 규칙)를 가진 항목이 있으면 건너뛴다 — today.md 안에서 같은 단어/문장이 여러 번 등록되어 있어도(예: `sample-today.md`의 `deadline` 중복) 한 번만 추가된다. 새로 추가된 항목이 있을 때만 저장소를 `Save()`한다.
* 이 설계 덕분에 **가져오기를 여러 번 실행해도 안전하다(idempotent)** — today.md를 지우지 않으므로 다시 실행해도 새 항목만 추가되고 기존 항목은 중복으로 건너뛴다. 그래서 가져오기 실행 후 today.md를 비우거나 수정할 필요가 없다 — 파일은 그대로 둔다.
* 가져오기가 끝나면 읽기 창은 단어/영작 데이터를 다시 병합해(§26.2) 팝업에 즉시 반영하고, "단어 N개 추가, 중복 K개 건너뜀" 메시지를 보여준다.
